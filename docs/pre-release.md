# Pre-release / deploy runbook (operator)

Operator track — the checklist to run **before** the first real-user release and
on every subsequent production deploy. Assumes the Cloudflare-Workers monorepo
(`apps/web`, `apps/mail-in`, `apps/mail-jobs`, plus `landing`/`docs`). Written
2026-07-28.

Two kinds of item live here:

- **One-time hardening** — done once before release, then it stays done.
- **Every-deploy** — part of the normal deploy sequence forever.

---

## 0. One-time hardening (before first release)

### 0.1 Remove the R2 plaintext-tolerance patch — **fail closed**

`packages/mail-core/src/crypto.ts` `unpackBlob` still tolerates un-encrypted
blobs so that mail written *before* at-rest encryption keeps rendering:

```ts
// crypto.ts (~line 138)
if (blob[0] !== BLOB_V1) return blob; // pre-encryption plaintext (un-gzipped)
```

This is a deliberate temporary compatibility shim. **Before release, delete that
line** so `unpackBlob` throws on any non-`BLOB_V1` envelope — the same
fail-closed behaviour `getDecryptedBlob`/`decryptBytes` already enforce. After
the test-data wipe there is no legacy plaintext left in R2, so nothing should
hit it; keeping it past release is a silent "encryption optional" hole.

Gate: `crypto-blob.test.ts` has a case asserting the tolerance path — flip it to
expect a throw when you remove the shim. See memory
`remove-r2-plaintext-tolerance-before-release`.

### 0.2 Known gap — draft-staged attachments are still plaintext in R2

Encrypted-at-rest today: inbound RFC822 raw, outbound JSON body, staged inbound
attachments. **Not** encrypted: **draft-staged attachments** (a file attached
while composing, before send). It is:

- transient — lives only while the draft is open,
- re-encrypted the moment the draft hits outbound (`copyToOutbound` encrypts),
- low-volume, off the receive/send hot path.

So it is not a live-test blocker, but it is the **last plaintext content path**.
Do **not** ship the flat claim "all mail content is encrypted at rest" while this
gap exists — either close it (encrypt `stageDraftAttachment`, decrypt in
`readDraftAttachment`, thread the `ck`; ~one path + tests) or footnote the claim.
Decision as of 2026-07-28: **deferred, release-blocker, recorded here.**

### 0.3 Secrets present in every environment

Encrypted secrets survive deploys (unlike plaintext dashboard vars). Set once per
Worker env that needs them:

| Secret | Used by | Purpose |
| --- | --- | --- |
| `MAIL_DEK` | web, mail-in, mail-jobs | AES-256-GCM data-encryption key for content + R2 blobs (`importKey`). |
| `MAIL_SEARCH_KEY` | web, mail-in, mail-jobs | HMAC key for blind search tokens **and** signed resource/image tokens. |
| `VAPID_PUBLIC_KEY` | web | Web-push application server key (client subscribes with it). |
| `VAPID_PRIVATE_KEY` | web | Web-push signing key. Keypair generated by the VAPID keygen step; the private key never leaves secrets. |

`wrangler secret put <NAME> --env <env>` per Worker. Losing `MAIL_DEK` = all
stored mail is unreadable — back it up out-of-band.

### 0.4 Move non-secret vars into wrangler configs

`keep_vars: true` is set on `apps/web`, `apps/mail-in`, `apps/mail-jobs` so a
deploy doesn't wipe dashboard-set plaintext vars. The clean end-state is to stop
relying on dashboard vars entirely: declare every non-secret var in each
`wrangler.jsonc` `vars` block so config is reproducible. Track remaining
dashboard-only vars and migrate them in. See memory
`cloudflare-vars-deploy-wipe`.

### 0.5 Infrastructure (IaC + provisioning prereqs)

Each Worker's `wrangler.jsonc` is the **declarative source of truth for
bindings** — D1, R2, KV, queues, Durable Objects, `send_email`, routes. `wrangler
deploy` reconciles bindings, but it does **not** create the stateful resources
they point at, and it does not touch Email Routing or Email Service. Those are
provisioned once, imperatively, and their IDs pasted back into the configs. Until
that's templated per-env, `database_id` / KV `id` are hard-coded in the configs
(same D1 `doota` + same `AUTH_KV` shared across all three Workers) — a real
multi-env IaC pass would parameterize these.

**Workers and what they own** (single-purpose split — a queue binds one consumer):

| Worker | Config | Owns |
| --- | --- | --- |
| `doota` (web) | `apps/web/wrangler.jsonc` | App + `send_email`; **produces** to inbound/outbound queues; custom domain `mail.doota.dev`. |
| `doota-mail-inbound` | `apps/mail-in/wrangler.jsonc` | `email()` handler + **consumes** `doota-mail-inbound`. Name is load-bearing — the Email Routing catch-all targets it. |
| `doota-mail-jobs` | `apps/mail-jobs/wrangler.jsonc` | **Consumes** `doota-mail-outbound` + `doota-mail-events`; owns the `MailEventHub` DO; cron `*/5`. |

**Resources to create once (deploy will NOT create these):**

```
# D1 (id → all three configs' database_id)
wrangler d1 create doota

# R2 bucket (binding MAIL_RAW in all three)
wrangler r2 bucket create doota-mail-raw

# KV namespace (id → web + mail-in AUTH_KV)
wrangler kv namespace create AUTH_KV

# Queues
wrangler queues create doota-mail-inbound
wrangler queues create doota-mail-outbound
wrangler queues create doota-mail-events
```

**Wired in the dashboard (not in any wrangler file):**

- **Email Routing** — catch-all rule on the receiving domain → Worker
  `doota-mail-inbound`. Set at runtime via `domains.remote.ts`
  (`MAIL_IN_WORKER_NAME`); confirm the rule exists and points at that exact name.
- **Email Service event subscription** — on the sending domain → queue
  `doota-mail-events` (Dashboard → Email Service → Event subscriptions). Feeds
  delivered/bounced/complained back to `doota-mail-jobs`. Without it, only
  DSN-fallback bounce handling works.
- **DKIM / return-path** — set on the sending zone; the `send_email`
  (`EMAIL_SENDER`) binding uses it. Verify before real sends.
- **Custom domain** `mail.doota.dev` — declared in the web config `routes`, but
  the zone + DNS must exist.

**Cross-Worker wiring gotchas:**

- The **`MailEventHub` DO is defined in `doota-mail-jobs`** (with a `migrations`
  `new_sqlite_classes` tag) and bound **cross-script** from web + mail-in
  (`script_name: "doota-mail-jobs"`). **Deploy `doota-mail-jobs` first** so the
  class exists before the other two bind to it.
- **Deploy order:** `doota-mail-jobs` → `doota-mail-inbound` → `doota` (web).
- Migrations live at repo-root `../../drizzle` shared by all three
  (`migrations_dir`); apply once against the shared D1 (§1.2), not per-Worker.

## 1. Every-deploy sequence

Run in order.

### 1.1 Verify gates

```
pnpm --filter @doota/mail-core exec tsc --noEmit
cd apps/web && npx vitest run src/test/     # FULL suite, not touched-file — cross-file regressions
npx svelte-check --threshold error          # pre-existing vite.config.ts error is ignorable
```

### 1.2 Apply migrations

Migrations run through `0028`. Apply remote in order:

```
wrangler d1 migrations apply doota --remote
```

Split add/drop across two migration files when a rename would otherwise trigger
drizzle-kit's interactive prompt (see 0026 add / 0027 drop).

### 1.3 Bump caches when render/logic changes

- **`RENDER_CACHE_VERSION`** (`apps/web/src/lib/server/render-cache.ts`, currently
  `"13"`) — bump whenever the body-render or sanitize/strip logic changes. It keys
  the body cache, the ETag, and the attachment cache, so a bump forces every
  client + edge copy to re-fetch the patched render. **Bump it in the same commit
  as any render-logic change**, or users keep seeing the old render.
- **PWA precache / service-worker version** — the `$service-worker` `version`
  invalidates old precached build files on the next load; a normal build bumps it.
  Confirm the SW updated after deploy (old build assets shouldn't serve).

### 1.4 Deploy

Deploy in order — **`doota-mail-jobs` → `doota-mail-inbound` → `doota` (web)** —
so the `MailEventHub` DO class exists before the other two cross-script-bind to
it (§0.5). Secrets and `keep_vars` vars survive; confirm no plaintext var got
dropped.

### 1.5 Post-deploy smoke (live)

- Receive a real inbound (Gmail, Outlook, Apple) → renders, threads correctly.
- A marketing template (Mailchimp/Amazon) renders as an HTML frame, not text.
- Send + reply → wire threading intact, quoted parent stripped.
- Attachment upload → view → download round-trips (encrypted at rest).
- Dark mode + web-push notification fire.

## 2. Re-materialize runbook (operator, on render-logic change)

When the **derivation logic** changes (`isRichHtml`, forward-aware quote
stripping, `htmlKind`/`hasRemoteImages`/attachment-`inline` computation), existing
D1 rows keep their *old* derived flags until re-fetched. To back-fill live data
without waiting:

**Shape (recommended):** a one-off handler in `apps/mail-jobs` that walks every
`message`, reads its encrypted raw from R2 (`getDecryptedBlob`), re-runs the
derivation (`rawObjectToHtml` + the strip/classify path), and re-writes the
derived flags + body cache (`packBlob`). Reuses existing bindings + `MAIL_DEK`;
no new creds or surface. Trigger via `wrangler ... --remote` or a temporary
guarded route, then remove the trigger.

**When to build it:** not now — data is wiped and the derivation logic is still
settling, so a script written today re-materializes against moving logic. Build
the handler the **first time a render-logic change ships to live data**, and bump
`RENDER_CACHE_VERSION` alongside so un-re-materialized rows still render correctly
on demand. Until then this is a documented step, not code.
