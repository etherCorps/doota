You've [prepared your configuration](/self-hosting/configuration) — now ship
it. Doota deploys as **one stack**: the three Workers plus everything they
bind (D1, KV, R2, queues, the Durable Object, the email sender) are declared
in `infra/alchemy.run.ts`, and a single command reconciles your Cloudflare
account against that declaration. No manual resource creation, no ID wiring,
no secret-by-secret pushes — and required secrets you didn't provide are
minted automatically on the first run.

There are two ways to run that command. Pick one:

| Path | Best for | Auth |
| --- | --- | --- |
| [**A. From your machine**](#a-deploy-from-your-machine) | First deploy, personal instances, test stages | Browser sign-in, no token |
| [**B. From GitHub**](#b-auto-deploy-from-github) | Teams, production — every merge to `main` deploys itself | Two repository secrets |

Most people start with **A** to see their instance come up, then wire up
**B** so production stays current without touching a terminal.

<Aside type="note" title="Prerequisites">
  Node ≥ 22.18, pnpm, a clone of the repo with `pnpm install` run at the root
  **and** in `infra/` (`pnpm -C infra install`), and a Cloudflare account.
</Aside>

## A. Deploy from your machine

### 1. Sign in to Cloudflare

```sh
cd infra
pnpm alchemy login
```

Opens the browser for OAuth and saves a profile to `~/.alchemy`. One-time per
machine — no API token needed for this path.

### 2. Deploy

From the repository root:

```sh
pnpm infra:deploy
```

This builds the web app and deploys the stack. The first run creates
everything: database (with the full schema applied), bucket, KV, queues, and
the three Workers. When it finishes, the printed `webUrl` is your running
instance:

```
webUrl: https://doota-dev-yourname.your-account.workers.dev
```

<Aside type="tip" title="Where did this deploy go?">
  Every deploy targets a **stage** — by default `dev_<your-username>`, where
  every resource name is suffixed (`doota-dev-yourname`, …) and isolated.
  Production is its own explicit stage with the bare names:

  ```sh
  pnpm --filter @doota/infra deploy --stage production
  ```

  You cannot hit production by accident; you have to type it. Use your
  default stage to test the deploy end to end, then deploy production.
</Aside>

To preview what a deploy *would* change without touching anything:

```sh
pnpm infra:plan
```

### 3. Apply your configuration

If you filled `infra/.env` during [Configuration](/self-hosting/configuration),
it was already applied. Changing config later is the same motion: edit
`infra/.env`, run `pnpm infra:deploy` again — config re-applies on every
deploy, and only the changes go out.

<Aside type="danger" title="MAIL_DEK is still precious">
  Minted or provided, `MAIL_DEK` encrypts every stored message. The minted
  copy lives in the Alchemy state store in your Cloudflare account — don't
  destroy a stage whose mail you care about, and back the key up if you can.
  **Lose `MAIL_DEK` and every encrypted message is permanently
  unrecoverable.** See [Operations](/self-hosting/operations).
</Aside>

## B. Auto-deploy from GitHub

`.github/workflows/deploy.yml` deploys `--stage production` on **every push
to `main`** — a merged PR is a push, so once this is set up, shipping Doota
is just merging. No `alchemy login`, no `.env` file in CI; minted secrets
come from the state store.

### 1. Create the deploy token

In the Cloudflare dashboard: **My Profile → API Tokens → Create Custom
Token**, with:

- **Account**: Workers Scripts, D1, Workers KV Storage, Workers R2 Storage,
  Queues, Secrets Store — all *Edit*; Account Settings *Read*.
- **Zone** (each zone in `ORIGINS`): Workers Routes *Edit*, DNS *Edit*,
  Zone *Read*. Skip if you're workers.dev-only.

This is **not** the same token as `APP_CLOUDFLARE_API_TOKEN` —
[two tokens, two jobs](/self-hosting/cloudflare-api-token).

### 2. Set the repository secrets

Two are required:

| Repository secret | Value |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | The deploy token from step 1 |
| `CLOUDFLARE_ACCOUNT_ID` | Your account id |

Then add your [configuration](/self-hosting/configuration) values as
repository secrets (sensitive: `SETUP_TOKEN`, `APP_CLOUDFLARE_API_TOKEN`, …)
and variables (plain: `ORIGINS`, `LOG_LEVEL`, …) — the workflow forwards all
of them. Anything you leave unset follows the same rules as local deploys:
minted once into state, or feature-off.

### 3. Merge to main

That's the whole deployment procedure from here on. The workflow also has a
manual trigger (**Actions → Deploy → Run workflow**) for re-deploys and the
one-time adoption run below.

## Migrating from a wrangler deployment

Only relevant if you already run Doota deployed with `wrangler deploy`.
Alchemy must **adopt** your existing resources once, instead of creating new
ones:

<Steps>
  <Step title="Export every live secret">
    `MAIL_DEK`, `MAIL_SEARCH_KEY`, `BETTER_AUTH_SECRET`, the VAPID pair, and
    any optional ones you use. The stack replaces each Worker's entire
    binding set — without the live values it would bind freshly minted ones,
    and mail stored under the live `MAIL_DEK` becomes unreadable. The deploy
    warns loudly if production is about to get a minted key.
  </Step>
  <Step title="Check the KV namespace title">
    Adoption matches KV by dashboard **title** (`AUTH_KV`). A mismatch
    silently creates a new namespace.
  </Step>
  <Step title="Plan, then adopt">
    ```sh
    pnpm --filter @doota/infra plan   --stage production
    pnpm --filter @doota/infra deploy --stage production --adopt
    ```
    D1 is safe: the stack reads the same `d1_migrations` table wrangler
    wrote, so only pending migrations run.
  </Step>
  <Step title="Turn off competing deploys">
    Disable Workers Builds (or any CI running `wrangler deploy`) for these
    Workers — a later wrangler deploy would overwrite the stack's bindings.
  </Step>
</Steps>
